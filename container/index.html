Run the daemon in a container¶

The image ghcr.io/memcastle/memcastle runs the existing MemCastle daemon on Linux amd64 and arm64. Each version uses the exact executable and dashboard build from that version's GitHub release, with shared skills copied from the matching source checkout. Core ships no provider sources or agent-specific integrations.

Stable releases publish a full version tag, such as :X.Y.Z, after the GitHub release becomes public. :latest follows the latest stable GitHub release; prereleases do not publish images. Use a version tag for controlled upgrades, or an image digest (@sha256:…) to pin the complete runtime image. Published images have OCI labels generated by docker/metadata-action, including the version and release commit.

Docker¶

Export a shared secret of at least 16 characters, for example from your secret manager:

export MEMCASTLE_AUTH_TOKEN="$(openssl rand -hex 32)"
docker volume create memcastle-data
docker run -d --name memcastle \
  --restart unless-stopped --stop-timeout 30 \
  -p 127.0.0.1:8420:8420 \
  --mount type=volume,src=memcastle-data,dst=/data \
  -e MEMCASTLE_AUTH_ENABLED=true -e MEMCASTLE_AUTH_TOKEN \
  ghcr.io/memcastle/memcastle:latest

Retain the secret in your secret manager so clients and replacement containers can use it. The environment option above copies it from your shell without putting its value in command history. Container administrators can inspect container environment variables; use your platform's secret-management facilities.

The daemon is available at http://127.0.0.1:8420, with MCP at /mcp. For clients outside the host, put a TLS reverse proxy in front of it and keep authentication enabled; see Authentication. The database-admin endpoint is not started or exposed by the image.

Inspect startup and use the bundled CLI:

docker logs memcastle
curl --fail http://127.0.0.1:8420/api/health
docker exec memcastle memcastle status
docker exec memcastle memcastle search 'previous decision'
docker run --rm ghcr.io/memcastle/memcastle:latest --version

The entrypoint is the memcastle binary and the default command is serve. Arguments after the image replace serve, so pass serve explicitly when changing daemon arguments:

docker run --rm ghcr.io/memcastle/memcastle:latest serve --help

Use docker stop --time 30 memcastle to send SIGTERM directly to the daemon and allow jobs to drain. Increase this budget if you increase MEMCASTLE_JOBS_DRAIN_TIMEOUT_SECS or have long-lived HTTP connections. Use foreground serve in a container, rather than daemon start.

Podman¶

The same OCI image works with Podman, including rootless named volumes:

podman volume create memcastle-data
podman run -d --name memcastle --stop-timeout 30 \
  -p 127.0.0.1:8420:8420 -v memcastle-data:/data \
  -e MEMCASTLE_AUTH_ENABLED=true -e MEMCASTLE_AUTH_TOKEN \
  ghcr.io/memcastle/memcastle:latest
podman exec memcastle memcastle status

For rootless bind mounts, prepare ownership inside the user namespace with podman unshare chown for UID/GID 10001. On SELinux hosts, use an appropriate mount label, such as -v ./memcastle-data:/data:Z for a private bind mount. Named volumes avoid having to match host-directory ownership manually.

Storage and configuration¶

The process runs as UID/GID 10001:10001, without a root startup wrapper. Mount the whole /data directory to preserve the palace and its administrative configuration together. An empty Docker named volume inherits the image directory's ownership. For a host bind mount, create and assign the directory to UID/GID 10001 before starting the container. Only one daemon may use a given embedded palace at a time.

Path Purpose
/data/config/memcastle/config.toml Optional daemon configuration
/data/config/memcastle/miners/ Administrative miner files
/data/data/memcastle/default/ Default palace; embedded database in db/
/data/data/memcastle/ Installed plugins, sources and file-backed credentials beside the palace
/data/state/memcastle/run/ Daemon discovery metadata
/usr/local/share/memcastle/ Immutable installed runtime assets

These paths follow HOME=/data, XDG_CONFIG_HOME=/data/config, XDG_DATA_HOME=/data/data, and XDG_STATE_HOME=/data/state. Existing configuration overrides still apply. The image defaults MEMCASTLE_BIND=0.0.0.0 so published ports can reach it; the daemon outside a container still defaults to loopback.

To supply TOML, mount a file readable by UID 10001 at /data/config/memcastle/config.toml, or set MEMCASTLE_CONFIG to another mounted path. A read-only config mount prevents administrative commands from editing the miners/triggers stored in that file. Mount directories to be mined separately, for example -v /srv/project:/inputs/project:ro, and use the container path in miner configuration. Installed sources still need their normal permissions and any external programs they declare; the image does not install provider-specific helper programs.

Enable the packaged dashboard by adding -e MEMCASTLE_WEB_ENABLE=true to the container's environment. It is then served at /ui; see Web UI for login and client behavior.

Remote SurrealDB¶

Use the existing remote-store TOML configuration, mounted as described above:

[store]
mode = "remote"
url = "wss://database.example.com"
namespace = "memcastle"
database = "main"
username = "root"
password = "replace-with-your-database-secret"

Keep this file owner-readable and provision it through your deployment's secret manager. Only root sign-in is currently supported, and remote-store settings currently require TOML. localhost in this URL means the container itself, not another container or the host. See Storage and data for the backend contract.

A remote database removes the need for a durable local database volume, but the daemon still writes local palace/discovery directories and may keep source packages, configuration and credentials locally. Provision or persist those explicitly; use writable ephemeral /data storage only when those files are disposable. A read-only root filesystem can be used with writable /data and a /tmp tmpfs. This container deployment does not validate multi-replica operation or synchronize daemon-local files between replicas.

Ports and health¶

To change the internal port, set MEMCASTLE_PORT, for example -e MEMCASTLE_PORT=9000 -p 127.0.0.1:9000:9000. The generic hosting-platform variable PORT is not read. The built-in health check runs memcastle status, using the daemon registry to discover its actual address. It honors bind/port changes without a separate probe configuration.

GET /api/health is public HTTP liveness, not datastore-aware readiness. The HTTP server starts after startup connection/migration, but this endpoint does not detect a later database outage. Docker runs the status check every 30 seconds, with a 60-second startup grace period and three attempts before marking unhealthy. Adjust the startup budget for a large migration.

Upgrades and backups¶

Stop the old container, back up the persistent data and configuration, then create its replacement using the same volume and authentication secret with the new version tag. Startup applies the normal database migrations; see Migrations and upgrades. Do not run old and new containers against the same embedded volume concurrently. Do not assume downgrading an image reverses database migrations.

Build locally¶

The root-level Dockerfile copies the executable, frontend build and skills directly from the checkout. Build the local image with the existing Rust/frontend tasks:

mise run docker
docker run -d --name memcastle-test memcastle:local
# Once the daemon has started:
docker run --rm --network container:memcastle-test memcastle:local status
docker rm -f memcastle-test

If target/debug/memcastle and web/dist are already built, docker build --tag memcastle:local . is sufficient. The executable must target Linux and the chosen image architecture. The Dockerfile does not compile anything; BIN and WEB select other existing inputs relative to the build context:

docker build --tag memcastle:local \
  --build-arg BIN=path/to/linux/memcastle \
  --build-arg WEB=path/to/frontend/build .

The installed frontend lives at /usr/local/share/memcastle/web/index.html; the checkout's frontend remains under web/dist. The image uses debian:stable-slim and its normal package repositories, so rebuilding can refresh runtime packages while keeping the release executable and assets unchanged.

Pull-request CI reuses its existing Linux executables and frontend build directly, builds both images on ubuntu-latest, and checks daemon status with an inline docker run plus a dashboard request; arm64 uses QEMU. The post-release Container workflow verifies the published raw executables and frontend archive, then passes those inputs directly to the Dockerfile for each architecture. It checks daemon status before publishing a multi-platform image with an SBOM and build provenance. Its manual tag input retries publication without another Rust build. Retries can refresh a version's runtime image; use a digest to pin the entire image. Retries of older releases cannot move latest backwards. The release tag must contain the container packaging files for automated publication.

Signatures and attestations¶

The publication workflow signs the multi-platform image digest with Cosign using GitHub Actions' OIDC identity. It also publishes a signed GitHub build-provenance attestation to the registry. No signing key is stored in repository secrets.

Verify a published image by digest, replacing the placeholder below with its actual digest:

image=ghcr.io/memcastle/memcastle@sha256:IMAGE_DIGEST
cosign verify "$image" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github\.com/memcastle/memcastle/\.github/workflows/container\.yaml@refs/(tags/[0-9]+\.[0-9]+\.[0-9]+|heads/main)$'
gh attestation verify "oci://$image" --repo memcastle/memcastle
